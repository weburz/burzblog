# Contributing

Thanks for helping. Please follow the [Code of Conduct](CODE_OF_CONDUCT.md).
Read `AGENTS.md` and `docs/architecture.md` first; report security
problems privately as described in [SECURITY.md](SECURITY.md).

## Proposing changes

Open an issue before starting anything bigger than a small fix, so we can agree
on the approach first. Bug fixes and documentation improvements can go straight
to a pull request.

## Setup and everyday commands

Prerequisites are listed in the [README](README.md#development).

```sh
task setup     # Go modules, pnpm dependencies, the Playwright browser
task dev       # API on :8080 (data in ./burzblog-data) and the panel on :3000
task check     # the merge gate: Go and panel checks, browser E2E, pre-commit hooks
task format    # gofmt and oxfmt
```

The browser E2E tests build the real binary and listen on 127.0.0.1:3000 by
default. Set `E2E_PORT` to use another port while `task dev` holds :3000, for
example `E2E_PORT=3300 task check`. A port that is already in use fails the run
instead of being reused. The tests use a disposable data directory; never point
them at real content.

`task docker:check` lints, builds and smoke-tests the container image; run it
when you touch the Dockerfile, `compose*.yaml` or `deploy/`.

## Where things live

- `cmd/burzblog`: the entry point.
- `internal/post`: model, validation, frontmatter; no IO.
- `internal/store`: SQLite, migrations in order; never edit a shipped migration.
- `internal/auth`: passwords, sessions, tokens, rate limiting.
- `internal/render`: goldmark and bluemonday.
- `internal/server`: HTTP.
- `internal/client` and `internal/cli`: the terminal client.
- `internal/panel/dist`: generated by `scripts/embed-panel.sh`; never commit or
  hand-edit it.
- `web/`: the Nuxt panel.
- `docs/`: guides; `docs/architecture.md` describes how BurzBlog is built.

## Code

Go code follows the Google Go style guide, is formatted with gofmt and handles
errors explicitly with messages that tell people what to do. Tests use the
standard `testing` package with positive and negative cases; anything touching
the database or files uses temporary directories. The panel uses Nuxt UI, arrow
functions, Vitest for units and Playwright for end-to-end tests.

Every change to a post goes through `store.UpdatePost` with the version the
caller started from. Store migrations are append-only: add a new entry to
`migrations` in `internal/store/store.go`, never edit one that has shipped.

Review dependency updates deliberately: `go get` then `go mod tidy` for Go,
pnpm for the panel. Never hand-edit `go.sum` or the pnpm lockfile. No code
should be copied from other projects without a provenance and license review.

## Branches, commits and pull requests

Use short-lived feature branches and never push to `main` directly. Commit
subjects are [Conventional Commits](https://www.conventionalcommits.org/)
(`feat(store): describe the change`), lowercase after the type, no trailing
period, 50 characters at most. The `crisp` commit-msg hook enforces this; install the
hooks with `pre-commit install` and check a message with
`crisp message 'feat(store): describe the change'`.

Open a PR using the template, with the exact verification commands and results
and any limitations. GitHub Actions is intentionally disabled, so run
`task check` locally and record the result in the PR. Do not bypass reviews.

Contributions are accepted under the repository's Apache-2.0 license
(`LICENSE`); there is no CLA and no sign-off requirement.
